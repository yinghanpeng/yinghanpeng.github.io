## 核心判断：模型幻觉是全链路问题

我认为，模型幻觉不能只从某一个环节去思考，更不能简单归结为“模型答错了”。在 Agent 工程中，应该把观察范围拉长到整个决策生命周期：Agent 处于什么状态、接收了什么信息、做出了什么判断、调用了什么工具、如何理解工具结果，以及最终怎样组织输出。

很多幻觉并不是在最后生成答案时突然出现的，而是前面的某个环节已经产生偏差。错误状态会带来错误判断，错误判断会触发错误动作，错误动作又会形成错误观察，最后模型只是把整条错误链路组织成了一个看起来合理的答案。

因此，治理幻觉的关键不是寻找某一个“万能开关”，而是检查整个 Agent 系统的证据链、状态链和决策链。

## 一、提示词与目标定义

首先要检查的是提示词和任务目标。

- 是否给 Agent 定义了明确的角色和职责边界？
- 任务目标是否足够清晰？
- 成功标准和失败条件是否明确？
- 是否告诉模型在证据不足时应该如何处理？
- 是否限制它只能基于已有证据回答，而不是自由扩散？

如果目标本身模糊，Agent 就只能在不完整的约束下自行补全意图。这种“主动补全”在体验上可能显得聪明，但在工程系统中很容易成为幻觉的起点。

## 二、记忆系统中的幻觉来源

### 短期记忆

短期记忆通常和上下文压缩、窗口裁剪有关。比如系统只保留或重点压缩最近六轮对话，但真正重要的信息可能出现在更早的位置。如果压缩策略只考虑“近”，没有考虑“重要”，关键约束就可能被丢失。

因此，短期记忆的压缩不能只依据轮次，还要识别并保留：

- 用户的核心目标；
- 已确认的事实和约束；
- 尚未解决的问题；
- 工具调用结果；
- 会影响后续决策的状态。

### 长期记忆

长期记忆的问题更多出现在写入质量和生命周期管理上。

- 写入的内容是否包含噪声或未经确认的信息？
- 重要的用户偏好和项目约定是否真正写入？
- 每条记忆是否保留来源和时间？
- 新旧记忆冲突时，是直接覆盖，还是向用户确认？
- 是否为可能失效的信息设置过期时间？

长期记忆一旦写错，错误就可能跨会话复用。相比一次回答中的幻觉，这类问题更隐蔽，因为它会在后续任务中被当作既有事实反复使用。

## 三、Tool Calling 中的幻觉来源

工具调用是 Agent 从“回答问题”走向“执行任务”的关键环节，也是非常容易产生链路错误的地方。

需要检查：

- Agent 是否选择了正确的工具；
- Tool Schema 是否定义清晰；
- 多个工具之间是否存在过度相似的描述，导致选择困难；
- 调用参数是否完整、类型是否正确；
- 工具返回结果是否被正确解析；
- 工具调用失败时，Agent 是否错误地假设执行成功。

工具调用必须留痕。系统应该能够验证“工具是否真的被调用”“参数是什么”“返回了什么”，而不能只根据模型的自然语言描述判断任务是否完成。

## 四、RAG 离线知识库的质量

RAG 的问题可以分成离线知识库构建和在线检索两个阶段。

### 文档质量与覆盖范围

首先要判断知识库中的文档质量如何，是否真正覆盖用户的问题，内容是否过期，来源是否可信。如果正确答案根本不存在于知识库中，后续再复杂的检索优化也无法解决问题。

### 文档切分策略

切分块过大，单个块里会混入多个主题，造成语义稀疏；切分块过小，又可能破坏完整语义，让关键上下文分散在不同块中。

切分策略需要结合文档类型选择，并尽量保留标题层级、段落关系和必要的重叠区域，而不是只按固定字符数机械切分。

### Embedding 模型

Embedding 模型要匹配语种和领域。如果知识库以中文为主，可以评估 BGE、Qwen 等更适合中文语义的模型；垂直领域还要验证模型是否能区分专业概念，而不能只看通用榜单。

### 向量索引

索引类型和索引参数同样会影响召回效果。召回率较低时，需要检查向量索引、Elasticsearch 检索参数以及近似搜索相关配置，而不是立即把问题归咎于大模型。

## 五、RAG 在线检索与排序

在线检索阶段首先要保证：查询时使用的 Embedding 模型与入库时一致。模型或向量空间不一致，会直接破坏相似度结果。

其次，可以采用 Hybrid Search，把关键词检索和向量检索结合起来。但“做了混合检索”并不代表结果一定正确，还要继续检查：

- 多路结果如何融合；
- 使用加权融合还是其他融合策略；
- 各路权重是否适合当前业务；
- Top-K 是否设置合理；
- 是否需要增加 Re-rank。

有时 `Recall@K` 已经很高，相关文档也确实被召回了，但它们排在结果列表的后面。此时问题不在召回，而在排序，需要重新评估 Re-rank 模型和排序策略。

## 六、上下文工程与压缩

为了控制成本、避免上下文污染和上下文腐烂，系统通常会压缩 RAG 内容和工具返回结果。但压缩本身也可能制造幻觉。

需要关注：

- 压缩时是否保留了关键结论和限定条件；
- 是否保留信息来源；
- 是否破坏了原有结构；
- 是否把“不确定”压缩成了“确定”；
- 多个来源冲突时是否仍能看出冲突关系。

相比一段没有结构的摘要，我更倾向于结构化压缩，例如保留“事实、来源、时间、约束、待确认项”等字段。这样既能降低 Token 消耗，也更有利于后续校验。

## 七、输出前的证据与结果校验

Agent 输出之前，应该进行验证性判断。

- 声称调用工具时，是否真的存在工具调用记录？
- 声称来自知识库时，是否能关联到具体检索结果？
- 输出中的关键事实是否都有证据支持？
- 是否满足输出格式和业务约束？
- 证据不足时，是否明确表达不确定，而不是继续补全？

可以通过 Output Validation 限制模型只基于已有证据回答，减少无依据扩散。对于高风险场景，还可以增加规则校验、二次模型校验或人工确认节点。

## 八、从 Agent 范式分析幻觉

### ReAct

在 ReAct 中，幻觉可能出现在三个位置：

1. Reasoning 阶段做出了错误判断；
2. Action 阶段选择了错误工具或传递了错误参数；
3. Observation 阶段错误解析了工具返回结果。

因此，不能只校验最终答案，还要校验每一轮“推理—动作—观察”的轨迹。

### Plan and Execute

Plan and Execute 的风险在于错误传播。如果最初的规划就是错的，后续每一步往往都会沿着错误方向继续执行。

一种改进方式是固化关键流程，为规划提供明确的标准步骤，并使用 JSON 等结构化形式传递步骤之间的参数。同时，对每一步的输入、输出和执行结果设置检查点，而不是等整个计划执行结束后才发现方向错误。

## 九、模型层面的原因

从模型本身来看，大语言模型是在不断预测下一个 Token，因此天然存在生成错误内容的概率。训练数据覆盖不足、数据质量不高、缺少垂直领域知识，都会提高幻觉风险。

另一个问题来自对齐阶段。如果奖励机制更强调 Helpfulness，而 Truthfulness 的权重不足，模型可能更倾向于“给出一个有帮助的答案”，而不是承认自己不知道。

因此，在训练和评估阶段可以考虑：

- 提高事实正确性的奖励权重；
- 对关键事实错误设置强约束或一票否决；
- 奖励模型在证据不足时明确拒答或请求补充信息；
- 使用垂直领域数据补足模型能力；
- 把真实性、可验证性纳入独立评测集。

## 十、我的工程化治理思路

综合来看，我更倾向于用分层防御的方式治理模型幻觉：

1. 在提示词层定义角色、目标和边界；
2. 在记忆层治理写入、冲突和过期；
3. 在工具层约束选择、参数和执行留痕；
4. 在 RAG 层分别评估知识库、召回、融合和排序；
5. 在上下文层保留结构、来源和关键约束；
6. 在 Agent 轨迹中校验每一步决策；
7. 在输出层建立证据约束和结果验证；
8. 在模型层持续优化数据、训练和评测策略。

模型幻觉不是一个单点 Bug，而是一类系统性问题。真正有效的治理方式，是让 Agent 的每个关键判断都有上下文依据，每次工具调用都有执行记录，每个重要结论都有证据来源，并且在证据不足时能够停下来，而不是继续生成一个看起来合理的答案。
